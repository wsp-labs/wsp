# Startup intent and review follow-up

Both CLI and MCP use subStart. That helper now sends the requested prompt and picks through one SubStartIntent with workspaces.create, before provisioning, while retaining the same picks for the subsequent agent start. Both setup strategies retain this intent on the workspace record; connected creation events carry it from their first stage. The pending view draws the opening message and its composer reads the requested agent/model/effort rather than unrelated local defaults. Requested picks are provisional until session.start reports accepted picks. This shares the startup contract and existing StartupLine; it does not replace the distinct provider allocation and shared-compute policies with one provider queue.

Greptile's new P1s reproduced before changes: sessions.delete chose the owner-only delete permission for isolated children; an isolated checkout admitted several conversations and then deleted all of them; a Git pack omitted submodule checkout contents and their current work. The first now recognizes the authenticated opener, the second shares the one-conversation guard and retains legacy extra conversations on deletion, and the third refuses projects with Gitlink entries instead of reporting an incomplete copy as successful. Submodule transfer itself is not implemented. The earlier saved-key refresh and broker-retry findings already have focused regression coverage on this branch.

Lifecycle: one runtime is owned by a lead tree and connected computer, while each child has its own checkout and branch. A finished turn leaves its checkout available for another message. merge_in returns committed work through the link and marks the returned head; it does not delete the checkout. Ending the lead's turn is not settlement. Explicitly settling the root triggers cleanup only once all its children are inactive and all checkouts pass dirty-file, ignored-data and unreturned-commit checks. A plain folder cannot pass Git-result cleanup and is retained for export. A deletion removes only the child's checkout while siblings remain; removing the last safe checkout deletes the runtime. Cleanup failures keep the ownership record for retry. After release, a new message recreates the checkout from its source's current checkout; the host keeps the conversation, but the released filesystem is not restored as a checkpoint. There is no provider expiry timer on this path.

Area-note proposals: the isolated-child opener uses the same delete_sub permission gate as a provider child; a child checkout accepts one conversation, and legacy extra conversations must survive individual deletion; a checkout copy must refuse Gitlinks until submodule files and current work can travel safely; setup intent is provisional display data and must not enqueue a duplicate agent start in the app.

Follow-up validation: 251 focused startup, transfer, deletion, live-transcript and setup tests passed; 575 stable-tree law tests passed with 22 gated skips; the refreshed MCP record checks and 116 Rust MCP library tests passed. The broader Rust replay stops at the unrelated thread_head fake-host page check before reaching run. This same failure reproduces at the previous branch head 4f85f8cb7 in a disposable worktree. The standalone size check also reports the same 1510-line sessions.ts and 2022-line ops.rs at that prior head; this follow-up does not increase either file's line count. Generic main-merge assumptions remain inapplicable to the pinned stable hotfix. None of these failures is represented as a green release gate.
